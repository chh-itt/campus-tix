## 0. 项目 30 秒介绍（开场必背）

> CampusTix 是我独立完成的校园活动票务平台，覆盖「活动发布 → 场次售票 → 下单支付 → 出票核销 → 退款/候补」完整交易闭环。技术栈 Spring Boot 3 + MySQL + Redis + RocketMQ + MyBatis-Plus + Vue3，Docker Compose 一键部署。我做这个项目主要是想补齐常规业务开发里最核心的几块：高并发下单防超卖、接口幂等、订单状态机、延迟消息关单、支付回调，每一个都用测试和压测验证过。

一句话版本：**「一个覆盖完整交易闭环的校园票务系统，重点解决了防超卖、幂等、订单状态机、超时关单四个高并发经典问题。」**

## 1. 防超卖（简历第一条，必被深挖）

### 简历表述
Redis Lua 原子预扣前置削峰 + 数据库条件更新权威兜底的双层库存模型；Testcontainers 集成测试 8 用户并发抢 2 票，成功恰 2、超卖 0。

### 为什么需要两层？
- 只用 DB：`UPDATE ... WHERE remaining >= N` 每次都要走行锁，热点场次几千人同时抢，大量请求阻塞在锁上，RT 飙升、连接池打满。
- 只用 Redis：Redis 宕机/数据丢失时库存就错了；而且订单最终落库还是要写 DB。
- 所以：**Redis 挡流量（99% 的失败请求到不了 DB），DB 保正确（库存的权威值）**。

### Redis 侧怎么做原子性？（追问：为什么不先 GET 再 DECR？）
- GET 再 DECR 两步之间有并发窗口，会超扣。用一段 Lua 脚本把「读取-判断-扣减」合并成原子操作：
  ```lua
  local stock = tonumber(redis.call('GET', KEYS[1]))
  if not stock then return -1 end      -- key 不存在，调用方从 DB 恢复
  if stock < tonumber(ARGV[1]) then return 0 end  -- 库存不足
  return redis.call('DECRBY', KEYS[1], ARGV[1])
  ```
- Redis 单线程执行脚本，天然串行，无锁。

### DB 侧怎么做？（追问：为什么不用 SELECT FOR UPDATE？）
- 条件更新（乐观思路）：`UPDATE t_activity_session SET remaining=remaining-#{q}, sold=sold+#{q} WHERE id=#{id} AND remaining>=#{q}`，影响行数=0 就是没抢到。
- 不用 `SELECT FOR UPDATE`：悲观锁把整个事务串行化，冲突激烈时吞吐差；条件更新一条 SQL 原子完成，靠 InnoDB 行锁保证同一行的 UPDATE 串行。

### 完整下单流程（能把这串讲顺就赢了）
1. 幂等检查（token + 唯一索引）
2. 校验场次可售（ON_SALE、销售窗口内）
3. Redis Lua 预扣：不足 → 直接返回 SOLD_OUT（没有 DB 请求）
4. Redis 扣成功 → 开事务 → DB 条件扣减（失败 = Redis 多扣/超卖风险，回补 Redis）
5. 事务里：建订单（雪花 ID 拼订单号）+ 绑定幂等记录 + 事务提交后发延迟关单消息
6. finally：Redis 扣了但 DB 失败 → 回补 Redis；幂等没绑上 → 释放

### 追问弹药
- **Redis 扣成功但 DB 扣失败怎么办？** finally 里回补 Redis（INCRBY）；极端情况（进程崩溃）由定时对账任务兜底——库存 key 丢失/不一致时用 DB 的 remaining 重置。
- **Redis 宕机了怎么办？** 脚本返回 -1（key 不存在）时，从 DB 读 remaining 用 SETNX 初始化再重试一次；DB 变成唯一权威。
- **库存 key 什么时候初始化？** 主办方发布活动/添加场次时写入；启动时 DataSeeder/自愈逻辑 initIfAbsent。
- **为什么 8 并发抢 2 票的结果是「恰 2 成功」？** Redis Lua 保证扣减原子；DB 条件更新保证 `remaining>=N` 才成功；两层都不可能出现第 3 个成功订单。集成测试用 Testcontainers 起真 MySQL+Redis 验证。

## 2. 接口幂等（第二大必考点）

### 简历表述
幂等 token + Redis SETNX 占位 + 幂等表唯一索引三层防重，重复提交/网络重试返回原订单而非报错。

### 三层各自干什么？
1. **前端/客户端先领 token**（`GET /api/orders/token`，UUID）——保证每次「意图」只有一个令牌。
2. **Redis SETNX 占位**（`idem:aop:{scene}:{userId}`，TTL 10s）——同一用户同一场景 10 秒内重复点击直接拒绝（409 DUPLICATE_REQUEST），挡住连点。
3. **幂等表唯一索引**（`t_idempotency_record.token` UNIQUE）——占位成功但业务失败后重试，或者 Redis 被清了：插入唯一索引冲突 → 说明已经处理过 → 查出绑定的业务号返回原订单（幂等重放）。

### 关键细节（追问：为什么 SETNX 了还要唯一索引？）
- SETNX 有 TTL，过期后重试就挡不住了；进程重启 Redis 数据也可能丢。
- 唯一索引在 DB，是**最终防线**：`INSERT ... DuplicateKeyException` 判断已存在，再查 biz_no 返回原单。
- 绑定时机：订单**事务内**绑定（idempotency.bind），保证「订单插入成功」和「幂等记录绑定」原子；若事务回滚，绑定也回滚，token 可重用——不会出现「订单没建成但 token 永久失效」。

### 追问弹药
- **为什么不用「订单号防重」就够？** 下单请求是用户发起的，没有天然唯一 ID；token 就是我们发给用户的「请求 ID」。
- **幂等和防重是一回事吗？** 不是。防重=拒绝第二次（连点），幂等=第二次执行返回第一次的结果（重试安全）。三层里 SETNX 偏防重，唯一索引偏幂等。
- **支付回调的幂等怎么做？** 回调没有 token，靠订单状态机 CAS：`UPDATE ... SET status='PAID' WHERE order_no=? AND status='CREATED'`，影响行数 0 说明已处理过，直接返回 success（通知幂等）。

## 3. 订单状态机 + 超时关单（MQ 必问）

### 简历表述
CAS 单向状态流转（CREATED→PAID/CANCELLED/EXPIRED）；RocketMQ 延迟消息 + 定时兜底双通道关单，关单事务提交后释放库存并唤醒候补。

### 状态机怎么落地？
- 每次状态变更都是条件更新：`WHERE id=? AND status='旧状态'`（CAS），影响行数 0 = 状态已被别人改过 = 抛 ORDER_STATE_ERROR。
- 为什么不用 if 判断再 update？——「判断」和「更新」之间有并发窗口，两个线程都能把 CREATED 改成不同终态（比如同时支付+取消）。CAS 把判断和更新合成一步原子操作。

### 超时关单双通道
1. **主通道**：下单事务提交后发 RocketMQ 延迟消息（延迟级别对应支付 TTL），消费者收到时检查「确实还是 CREATED 且已过期」才关单——**消费也要幂等**，靠状态机 CAS 天然幂等。
2. **兜底通道**：定时任务每 30s 扫 `status=CREATED AND pay_expire_at<now` LIMIT 100 关单。为什么？MQ 消息可能丢、broker 可能宕机——**消息队列不承诺 100% 不丢，定时扫描是最终一致性的保险**。
3. **为什么事务提交后才发消息？** 事务内发消息，若事务回滚，消息已经出去了，消费者会关掉一个根本不存在的订单。用 `TransactionSynchronization.afterCommit` 保证「先提交，再发消息」。

### 关单后发生什么？（引出候补）
- CAS 置 EXPIRED/CANCELLED → DB 回补库存 → **事务提交后**发 `StockReleasedEvent`（事件监听在 afterCommit，避免「事务还没提交、候补逻辑读不到新库存」）→ 候补队首 CAS 抢占 → 自动创建限时订单。

### 迟到支付怎么办？（高频追问：关单和支付并发）
- 用户在第 119 秒支付，第 120 秒关单，两边同时到。谁先 CAS 成功谁赢：
  - 支付先：订单 PAID，关单消息到达时状态不是 CREATED，忽略。
  - 关单先：订单 EXPIRED，支付回调到达时发现状态是 EXPIRED → 进入**自动退款流程**（REFUNDING→REFUNDED，补记支付流水，通知用户）。
- 关键回答点：**不承诺两不并发，而是让任一顺序都能收敛到正确终态**。

### 追问弹药
- **RocketMQ 延迟消息原理？** 5.x 支持任意时间定时（TimerWheel）；我们用经典 18 个固定延迟级别（level 6=10s 等，配置可选级别）。面试说「固定级别延迟 + 消费端校验」即可。
- **为什么不用 Redis 过期回调？** 键过期通知不保证可靠（不重试、可能丢），且回调时机不精确。我们同时实现了 Redis ZSet 轮询版延迟队列作为无 MQ 环境的降级（delay-impl 可切换）——这一点说明我理解「可替换的基础设施抽象」。
- **定时任务多实例重复扫怎么办？** 扫描本身带 CAS 关单（幂等），重复执行无副作用；生产可加 ShedLock/分布式锁。

## 4. 支付（支付宝沙箱 + Mock 双通道）

### 简历表述
对接支付宝沙箱：RSA2 验签异步回调 + 回调幂等 + 迟到支付自动退款；内置 HMAC 签名的 Mock 收银台支持本地演示与自动化测试。

### 流程
1. 用户点支付 → 后端创建支付单（INIT，out_trade_no=订单号）→ 调支付宝 `pageExecute` 生成收银台表单 HTML。
2. 用户付款 → 支付宝**异步** POST `/api/payments/alipay/notify`。
3. 验签：`AlipaySignature.rsaCheckV1`（RSA2，用支付宝公钥验）——**防伪造回调**。
4. 校验金额（回调金额与订单金额 compareTo）→ 状态机 CAS 置 PAID → 出票（ticketNo 唯一）→ 通知。
5. 回调响应纯文本 `success`/`failure`（支付宝要求，非 JSON）。

### 追问弹药
- **为什么回调要验签？** 回调接口是公网可匿名访问的，不验签任何人都能 POST「支付成功」白嫖票。RSA2 验签用支付宝公钥验证签名，只有支付宝能构造。
- **验签过了就够吗？** 还要校验金额（防「1 分钱买 4 张票」）、校验 app_id、校验 out_trade_no 存在。
- **回调没收到/丢了？** 我们有「查单补偿」的思路：主动调 alipay.trade.query；本地实现里定时任务也会把 INIT 支付单与订单状态对齐（演示环境用 Mock 简化）。简历上写「验签+幂等+查单补偿思路」是安全的。
- **HMAC-SHA256 在 Mock 里干什么？** 模拟「网关才能造出合法回调」：签名密钥只有服务端知道，收银台 URL 带签名，回调必须验签——保证测试链路与真实链路「验签语义」一致。

## 5. 缓存一致性 + 三大经典问题（缓存必问）

### 简历表述
Cache-Aside + 空值缓存防穿透 + 随机 TTL 防雪崩 + SETNX 互斥防击穿；核销分布式锁防重复核销。

### 三个问题一句话说清
- **穿透**：查不存在的 id，每次都打到 DB。方案：空值也缓存（短 TTL 30s），后续同 id 查询命中空值直接返回。
- **击穿**：热点 key 过期瞬间，大量并发同时回源。方案：SETNX 抢互斥锁（10s TTL），抢到的查库回填，没抢到的等 50ms 重读缓存/直接读库（保证只有 1 个请求打 DB）。
- **雪崩**：大量 key 同时过期。方案：TTL 加随机抖动（60~90s）。

### 为什么用 Cache-Aside 而不是先更新缓存？
- 写：先更新 DB，再删缓存（而非更新缓存）。
- 原因：①更新缓存可能写入中间态且多数写不立即被读，浪费；②「删缓存」让下次读触发回源，简单且一致。
- **不一致窗口**：先 DB 后删缓存，两步之间读请求可能读到旧缓存——最终一致，票务详情页可接受（库存正确性不依赖缓存，靠双层库存模型）。

### 分布式锁（Redisson）
- 核销场景：`SETNX lock:ticket:{no}` 5s + DB CAS 双保险——锁挡并发，CAS 兜正确。Redisson 的 `tryLock` 底层是 Lua（加锁+过期时间原子设置），看门狗自动续期。

## 6. 候补机制（差异化亮点，别人简历没有）

### 流程
1. 售罄 → 用户加入候补（WAITING，同一场次同一用户仅一条活跃候补）。
2. 任意来源库存释放（超时关单/取消/退款）→ 事务提交后发 `StockReleasedEvent`。
3. 监听器按释放数量唤醒队首（`min(quantity, 5)` 次）：CAS 把 WAITING→NOTIFIED 抢占名额（CAS 失败=被别人抢了，继续下一个）→ 自动创建限时订单（10 分钟支付窗）→ 通知。
4. 候补单也超时 → 状态回 WAITING（名额让给下一位）/ 过期处理。

### 为什么用事件而不是直接同步调？
- 库存释放发生在「关单事务」里，直接调候补逻辑会把候补的耗时和失败耦合进关单事务；事件在 afterCommit 发布，**关单事务永远轻**，候补失败不影响关单。

## 9. 一图流架构（口述版）

```
Vue3 (5173/8088)
   │ /api
Spring Boot 3 (8080, 单体分层: controller/service/mapper)
   │                │                  │
   ▼                ▼                  ▼
 MySQL 8.0      Redis 7.2        RocketMQ 5.3
 (Flyway 9 表,  (库存Lua/幂等SETNX/ (延迟消息关单)
  条件更新扣库存, 缓存三防/分布式锁)
  幂等唯一索引)
   ▲
   └── Mock 收银台 / 支付宝沙箱回调（验签→幂等→出票）
```

- 为什么单体不上微服务？——业务量级不需要，单体反而能把并发/一致性做深；面试官反感「简历堆微服务但讲不深」。

## 10. 高频八股速答（结合本项目说）

| 问题 | 结合项目的答法 |
|---|---|
| 事务失效场景 | 下单里「事务内发延迟消息」的坑：改为 afterCommit 发送；同类事务自调用失效用 self 注入解决 |
| @Transactional 原理 | Spring AOP 代理，self 注入（@Lazy）拿到代理对象才能让内部调用走事务 |
| Redis 为什么快 | 内存 + 单线程无锁竞争 + IO 多路复用；我们的 Lua 扣减正是利用单线程原子性 |
| 缓存与 DB 双写不一致 | 先更 DB 后删缓存 + 短不一致窗口可接受；库存正确性不靠缓存 |
| MySQL 索引失效 | 条件更新走主键；列表查询组合索引；FULLTEXT ngram 处理中文 |
| 消息丢失 | 生产者 confirm/事务后发送、broker 刷盘、消费幂等 + 定时兜底扫描 |
| 分布式锁 | Redisson 看门狗续期；我们核销是 SETNX+CAS 双层 |
| 接口幂等 | token+SETNX+唯一索引三层（本项目完整落地） |
| 雪花 ID 时钟回拨 | MyBatis-Plus IdWorker 内置处理；我们用雪花 ID 拼订单号保趋势递增 |
